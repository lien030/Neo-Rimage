# v0.1.1 architecture and validation

## Scheduling

JobManager owns the task lifecycle, preparation token, worker slot and byte reservation under one state lock. Reading, parsing, decoding and encoding take place outside that lock. Preparation runs at most once concurrently and looks ahead at most `min(2 × maximumConcurrency, 64)` runnable items. It can return a larger reservation request after dropping temporary parse state; it never blocks internally waiting for memory.

Items waiting for an expanded preparation reservation still count inside the lookahead window and may re-enter preparation even when that window is full. Otherwise a fairness barrier could prevent cached small plans from draining while its large pending plan cannot finish preparation. The regression test fails with the old counting/admission rule and passes with the unified rule.

A prepared plan holds only source properties, target dimensions, resource estimates and SHA-256 fingerprints. It does not retain pixels, codec instances or SVG trees. The execution path reopens and verifies its bounded input before reconstructing the decoder. SVG resource fingerprints are checked too. Retry discards the old plan, and stale preparation tokens/attempts cannot affect the new attempt. Reservations for cancelled preparation remain charged until the preparation callback exits, including when its job is removed.

Processing admission atomically checks the runnable job, worker availability and shared memory. Queue reasons distinguish preparation, concurrency and memory; waiting-for-memory counts are a subset of queued counts. Smaller fitting images can bypass a blocked image eight times before the manager stops unrelated admission. Pause/cancel remove that item's barrier. Execution completion, errors, panics and thread creation errors return reservations. Shutdown waits for preparation and processing.

The startup budget is approximately half available memory, falling back to 512 MiB. PipelineCost is extended for the maximum pixel count across the entire operation chain, actual source sample/channel layout, parser/input buffers, colour conversion and encoding. TIFF Float32 uses four bytes per sample. This is conservative estimate-based admission, not an OS memory sandbox.

## Measured mixed batch

Windows x64 release build; 12 SVG/PPM inputs (512–1536 px sides), AVIF output at speed 8, fixed shared budget 512 MiB. `src-tauri/examples/mixed-batch.rs` measures simultaneous **actual executor calls**, rather than counting assigned slots. PowerShell samples process working set and thread count at 10 ms intervals.

| Workers | Duration | Images/s | Overlapping executions | Peak working set | Peak threads |
| --- | --- | --- | --- | --- | --- |
| 1 | 14.119 s | 0.850 | 1 | 102.48 MiB | 7 |
| 4 | 7.640 s | 1.571 | 4 | 204.96 MiB | 8 |

This workload improved throughput by about 1.85× with four workers in the final implementation. Results are machine/workload-specific, not a general performance promise. Working set is sampled, not an exact allocation trace. System fonts and runtime overhead are included in RSS, outside task reservation accounting.

## Reproduce

```powershell
. ./tools/build-windows.ps1 -DependenciesOnly
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib
cargo test --locked --manifest-path src-tauri/Cargo.toml -p rimage --lib
cargo clippy --locked --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
pnpm test
pnpm contracts:check
pnpm build
cargo build --locked --manifest-path src-tauri/Cargo.toml --release --example mixed-batch
./src-tauri/target/release/examples/mixed-batch.exe 1
./src-tauri/target/release/examples/mixed-batch.exe 4
```

## Validation boundary

Automated tests cover scheduling/resource admission, preflight caps, stale cancellation/retry callbacks, formats, source changes, SVG resource boundaries, output transactions, existing encoders and all three homepage languages. Native codec fixtures are generated in tests; two libavif rejection samples have pinned provenance and accompanying license text.

Validation on the development host: 91 application Rust tests, 147 rimage tests, and 90 frontend/tool tests pass, along with strict application Clippy, IPC contract checking and the production frontend build. Format checks include real 12-bit AV1 SDR/PQ/HLG sequences, container-only PQ detection, TIFF Deflate/LZW/JPEG/Fax4/Float32 and malformed SVG data resources. Packed low-bit TIFF grayscale is expanded before encoding, and TIFF YCbCr8 uses full-range BT.601 conversion. Custom YCbCr colour coefficients/reference ranges and higher-depth YCbCr TIFF are rejected rather than silently rendered with the wrong colour transform.

Native-development regression: after unsetting PKG_CONFIG, PKG_CONFIG_PATH and both SYSTEM_DEPS_DAV1D variables, `pnpm tauri dev --no-watch` reuses the pinned native cache, compiles the debug EXE and starts it. The launcher automatically supplies the native environment to Windows dev/build commands without modifying the parent environment or global PATH. Its five tests cover argument forwarding, preparation failure, Windows dev/build setup and non-Windows/version passthrough.

The development host has dav1d/vcpkg build caches. NSIS/MSI and the portable ZIP build successfully; the ZIP contains every configured license resource. The EXE reports version 0.1.1, and PE imports contain no dav1d DLL. On this host, the release EXE starts outside the native build environment; all three homepage languages display Neo Rimage with the existing layout, and maximize/restore is exercised.

These checks do not replace a clean Windows VM test. Clean-host installer startup/conversion and installation/uninstallation still require a separate clean Windows environment before publishing. No such environment was available during this implementation. macOS/Linux builds are not validated.
